# Agent Error Handling and Observability Design

## Goal

Provide a consistent failure model for the streaming Agent runtime that lets users safely recover from failures while making every run diagnosable through error codes, structured logs, traces, metrics, and alerts.

The design covers the HTTP/SSE Agent interface, the Agent ReAct loop, model calls, tool execution, approvals, and JSONL conversation persistence. It preserves the existing durable `sessionId` conversation model.

## Outcomes

- Users receive clear, safe error messages and an explicit recovery action instead of raw Java exception text.
- A request gets at most one terminal SSE error event.
- Model/network failures are automatically retried exactly once only before the run has emitted text or executed a tool.
- A user can continue a durable conversation after a recoverable failure without replaying an unsafe action.
- Operators can navigate from an error code to a run, trace, logs, metrics, and alerts.

## Scope and Non-goals

In scope:

- Structured Agent error events and a stable code catalog.
- Run-level recovery state and centralized failure mapping.
- Model retry, safe tool retry classification, and operation de-duplication boundaries.
- Frontend recovery presentation and diagnostic copy support.
- Micrometer, OpenTelemetry-compatible tracing, structured logging, dashboards, and alert policies.

Out of scope:

- Replacing JSONL conversation storage.
- Guaranteed recovery across a process restart for an in-flight model stream or approval.
- Retrying non-idempotent tools automatically.
- Recording raw prompts, credentials, or complete tool payloads in observability systems.

## Identifiers and Run State

Every Agent execution owns the following identifiers:

- `sessionId`: the durable conversation identity already used by `SessionService`.
- `runId`: a UUID for one `/agent/loop` invocation.
- `traceId`: the distributed trace identity, propagated from the inbound request or generated by tracing instrumentation.

`RunContext` owns `sessionId`, `runId`, `traceId`, current phase, retry attempt, whether any output token was emitted, whether any tool was executed, and completed write-operation IDs. It is created once at the HTTP/Agent boundary and passed through the loop, model adapter, tool processor, approval flow, and observability layer.

The run phases are `SESSION_LOAD`, `MODEL_STREAM`, `TOOL_EXECUTION`, `AWAITING_APPROVAL`, `PERSISTENCE`, and `TERMINAL`. A terminal run is immutable; any later callback is ignored and logged at debug level.

## Public Error Contract

Replace `AgentEvent.Error(Throwable)` with a safe structured event. HTTP failures before SSE headers are written use a standard HTTP status with the same response shape. Failures after stream establishment use an SSE `error` event.

```json
{
  "type": "error",
  "code": "MODEL-TIMEOUT-001",
  "message": "模型服务暂时不可用，可重试或继续此会话。",
  "recoverable": true,
  "action": "RETRY",
  "sessionId": "...",
  "runId": "...",
  "traceId": "...",
  "retryAfterMs": 1000
}
```

`action` is an enum: `RETRY`, `CONTINUE_SESSION`, `REAUTHORIZE`, `START_NEW_SESSION`, and `CONTACT_SUPPORT`. The frontend must choose its UI from this value, never from exception messages. The browser shows the error code and offers a copy-diagnostics action containing only code, run ID, trace ID, and timestamp.

Exceptions, stack traces, raw model responses, system prompts, credentials, and complete tool arguments are never sent in an API/SSE error payload.

## Error Catalog

Codes follow `DOMAIN-CATEGORY-NUMBER`. The initial catalog is:

| Domain | Codes | Recovery |
| --- | --- | --- |
| Request | `REQUEST-INVALID-001` | Correct and submit again |
| Session | `SESSION-LOAD-001`, `SESSION-APPEND-002` | Start a new session or try later |
| Model | `MODEL-TIMEOUT-001`, `MODEL-UPSTREAM-002`, `MODEL-RATE_LIMIT-003`, `MODEL-OUTPUT_TRUNCATED-004` | Retry or continue based on run state |
| Stream | `STREAM-DISCONNECTED-001` | Continue the session |
| Agent limits | `AGENT-MAX_ROUNDS-001`, `AGENT-MAX_TOOL_CALLS-002` | Continue with a narrowed request |
| Tool | `TOOL-VALIDATION-001`, `TOOL-TRANSIENT-002`, `TOOL-FAILED-003` | Correct, retry if safe, or continue |
| Authorization | `AUTH-DENIED-001`, `APPROVAL-EXPIRED-001` | Reauthorize or request approval again |
| Internal | `INTERNAL-UNEXPECTED-001` | Retry, then contact support |

The catalog maps a typed internal cause to an HTTP status where relevant, a safe localized message, default recovery action, retryability, and severity. Individual tool implementations may provide a typed failure but cannot expose raw exceptions to the client.

## Recovery Rules

`RunFailureHandler` is the single component allowed to classify a thrown error, write failure telemetry, emit the terminal SSE error, and complete the sink. `ModelStreamAdapter`, `AgentLoopExecutor`, `ToolCallProcessor`, and `ApprovalManager` delegate failures to it; none independently emit a terminal error.

Automatic retry is allowed only when all conditions are true:

1. The error is a recognized transient model/network/rate-limit error.
2. No text or thinking delta has been emitted in the run.
3. No tool has begun execution.
4. The retry budget is unused.

The retry budget is one. The delay uses bounded exponential backoff with jitter and is included as `retryAfterMs` when exposed. Once output exists or a tool has been attempted, no automatic replay is allowed. The UI preserves received output and offers `CONTINUE_SESSION`; continuing sends the same `sessionId` and a new explicit recovery message, not the original message replay.

Tool definitions declare an execution safety class:

- `READ_ONLY`: may retry when the failure is transient.
- `IDEMPOTENT_WRITE`: receives an `operationId`; the tool backend must de-duplicate completion by this ID before a retry.
- `NON_IDEMPOTENT_WRITE`: never automatically retries; requires continuation or a fresh user approval.

`ToolCallProcessor` returns a structured `ToolOutcome` instead of converting an exception into an `Error: ...` string. The Agent loop records a sanitized tool result for model context and sends a mapped `AgentError` to the browser when the run must stop.

## Frontend Recovery Experience

The web client owns an `agentRecovery` state containing the last user message, `sessionId`, `runId`, `traceId`, received text, terminal event, and available action.

- During automatic retry, show a non-blocking “正在重试” state with the wait duration.
- On `RETRY`, offer a manual retry only when replay safety is true.
- On `CONTINUE_SESSION`, preserve generated content and submit an explicit continue instruction with the same `sessionId`.
- On `REAUTHORIZE`, reopen the approval/authorization flow.
- On `START_NEW_SESSION`, preserve a copyable draft but create a new conversation ID.
- On `CONTACT_SUPPORT`, show the short error code and diagnostic copy action.

A client abort is recorded separately from an unexpected stream failure. Refresh and reconnection must never resubmit the original message automatically.

## Observability

All Agent logs are JSON structured logs. Each record contains, whenever available, `traceId`, `runId`, `sessionId`, `errorCode`, `provider`, `model`, `toolName`, `retryAttempt`, `outcome`, and `durationMs`.

Required events:

- `agent.run.started`, `agent.run.completed`, `agent.run.failed`
- `model.request.started`, `model.request.completed`, `model.request.failed`, `model.request.retried`
- `tool.execution.started`, `tool.execution.completed`, `tool.execution.failed`
- `approval.requested`, `approval.decided`, `approval.expired`
- `session.load.failed`, `session.append.failed`
- `stream.client.disconnected`

Observability data must not include the user prompt, system prompt, API secrets, or full tool arguments/output. Use lengths, hashes, allowlisted metadata, or redacted summaries when correlation is required.

Tracing uses Spring Boot Actuator, Micrometer Tracing, and an OpenTelemetry exporter. The trace hierarchy is:

```text
HTTP /agent/loop
  agent.run
    session.load
    model.stream (one span per attempt)
    tool.execute (one span per tool)
    session.append
```

Provider request IDs, when available, are span attributes and never replace the application trace ID.

Required metrics:

- `agent_runs_total{outcome,error_code,provider,model}`
- `agent_run_duration_seconds`
- `agent_first_token_duration_seconds`
- `agent_retry_total{reason,provider}`
- `agent_stream_disconnect_total{source}`
- `agent_tool_execution_total{tool,outcome,error_code}`
- `agent_tool_duration_seconds{tool}`
- `agent_approval_total{decision}`
- `agent_session_store_total{operation,outcome}`
- `agent_active_runs`

## Alerts and Dashboards

Initial alert policy:

- Warning when `MODEL-*` failures exceed 5% over five minutes or first-token delivery is absent for three consecutive minutes; critical above 15%.
- Critical when `INTERNAL-UNEXPECTED-001` occurs three or more times in ten minutes.
- Critical when session read/write failure rate exceeds 1%.
- Warning when a tool failure rate is three times its 24-hour baseline with at least 20 samples.
- Warning when unexpected stream disconnections exceed 10%; filter client-initiated cancellation from the numerator.
- Product-quality warning when `AGENT-MAX_*` errors exceed 2%; do not page by default.

Dashboards group user experience, model/cost, tool/approval, and persistence/runtime. Each error panel links error code to representative run IDs, trace IDs, logs, and spans.

## Implementation Boundaries

Introduce these focused components:

- `AgentError`, `ErrorCode`, and `RecoveryAction` for the public contract.
- `RunContext` and `AgentRunService` for per-run state.
- `RunFailureHandler` for the single terminal failure path.
- `RetryPolicy` for bounded retry decisions.
- `ToolOutcome` and tool safety metadata for structured tool failures.
- `AgentObservability` for logs, tracing, and metrics.

`AgentLoopExecutor` remains responsible for ReAct orchestration. `ModelStreamAdapter` remains an SDK callback adapter but only reports failures to `RunFailureHandler`. `AgentController` and `AgentFacade` stay thin transport/API boundaries.

## Rollout

1. Add the error contract and serialization tests while retaining compatibility only where required by current clients.
2. Route loop, model, persistence, approval, and tool failures through the centralized handler; add retry and tool safety tests.
3. Add frontend recovery controls and SSE integration tests for each action.
4. Add metrics, tracing, dashboards, and alerts in observe-only mode; calibrate after one week before enabling paging.

## Acceptance Criteria

- No raw exception details reach the browser.
- Each failed run emits no more than one terminal error SSE event with `code`, `sessionId`, `runId`, and `traceId`.
- Only output-free, side-effect-free transient model failures automatically retry, and at most once.
- Stream interruption, truncation, approval expiry, session read/write failure, tool transient failure, and unknown failure each have a tested error code and action.
- Continuing a session cannot automatically duplicate a completed non-idempotent tool operation.
- A failed run is discoverable by its trace ID across logs, metrics, and spans.
- Alert rules distinguish client cancellation from infrastructure stream failures.
